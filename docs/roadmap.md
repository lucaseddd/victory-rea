# Research roadmap for correct, smooth 3D rendering

The target is 30 **rendered** FPS in the cutscene (C1) and first mission (M1), with correct geometry, ground contact, animation and rendering. At 30 FPS the frame budget is 33.33 ms. The order below reflects the current evidence and dependencies. Static investigations can proceed in parallel. Use the shared GPU reservation for every scene run.

### Geometry and physical ground

A missing rendered surface, late terrain tiles, a bad depth test and missing physical contact require different reproductions. Start with the same camera and simulation checkpoint, check whether the surface appears in depth/geometry output, and use an independent observation for contact. Check the indirect command signature, offsets and strides, count limiting, UAV-to-indirect visibility, and resource-view type and lifetime. Where the asset data never arrives or a producer publishes completion before refresh, compare guest physical pages, aliases and the runtime mirror. A public fork documents a separate simulation defect where data written by a GPU texture pass needed to be visible to a CPU physics consumer. That is evidence to test the feedback path, with no established cause for this report. [Microsoft ExecuteIndirect](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12graphicscommandlist-executeindirect) · [Microsoft resource binding](https://learn.microsoft.com/en-us/windows/win32/direct3d12/resource-binding) · [cool_fox findings](https://github.com/codec-d/cool_fox/blob/main/docs/findings.md)

### Facial animation and scene fidelity

Test speech across several shots, and a silent interval as a control. Sample lip aperture or region motion relative to stable head landmarks to separate mouth motion from camera, lighting and head turns. Trace animation time and inputs through joint transforms, morph weights where applicable, dispatch, buffer generation/barrier and the consuming draw. A changing input with constant deformation points to a different stage from static weights or late audio. The authors' blend-shape shader work gives a first place to verify in the candidate. This architecture remains a hypothesis until a pass or CPU path is identified. Separately inspect material bindings, exposure/lighting, depth/stencil and resolves on the first divergent render target. [Khronos morph-target tutorial](https://github.khronos.org/glTF-Tutorials/gltfTutorial/gltfTutorial_017_SimpleMorphTarget.html) · [fxceless pinned README](https://github.com/fxceless/victory-fork/blob/ceb9e1f7a0180e61961bfde85d69d24e2dd84b39/README.md) · [Microsoft PIX GPU captures](https://learn.microsoft.com/en-us/windows/win32/direct3dtools/pix/articles/gpu-captures/pix-gpu-captures)

### Performance, safety of attribution and acceptance

Instrument queues independently using timestamps plus queue frequency and clock calibration, and separate queue wait, execution, CPU observation of completion, and guest publication. Use PIX timing for lanes and CPU/file activity where available, plus a separate frame capture for pass and resource inspection. Do not add overlapping durations. Correlate DESC/PSO availability, residency and queue waits with p95 and occurrences of the defect. Use GPU validation and DRED in separate diagnostic runs; their overhead invalidates direct comparison to the baseline. DirectStorage or a faster disk can improve transition stalls if I/O is observed on the critical path. Storage completion must still publish the correct bytes. [Microsoft D3D12 timing](https://learn.microsoft.com/en-us/windows/win32/direct3d12/timing) · [PIX Timing Captures](https://learn.microsoft.com/en-us/windows/win32/direct3dtools/pix/articles/timing-captures/pix-timing-captures) · [D3D12 residency](https://learn.microsoft.com/en-us/windows/win32/direct3d12/residency) · [DRED](https://learn.microsoft.com/en-us/windows/pix/gpu-captures/tdr-debugging) · [Microsoft DirectStorage](https://github.com/microsoft/DirectStorage)

For each paired experiment, hash the executable, score schema, watchers and effective configuration. Use the same scene, checkpoints, save, render scale and frame generation state. Alternate the order and repeat comparably. Keep only text and aggregates in public Issues. Report duration, frame count, rendered FPS, median, p95, fraction above 33.33 ms, GPU loss/hitches, typical/peak VRAM, and the three independent image/contact/face checks. Score weights and existing brightness math remain versioned. Record unavailable checks explicitly and prevent them from qualifying a release. PresentMon can corroborate display events; it needs runtime correlation to validate title render IDs. [PresentMon source](https://github.com/GameTechDev/PresentMon/blob/main/PresentMon/PresentMon.hpp)

The first performance candidate should change only one measured cause. Restore missing work before counting gains: fewer draws, blank but bright images, lost animation, repeated frames, lower scale and frame generation can all change the apparent result without meeting the goal. Record how much remains above the 33.33 ms budget after the change.

## Deferred until evidence warrants it

Frame generation, reducing render scale, hardware replacement, broad fork merges, optional ray-tracing parity and redesign of presentation are lower-priority for this baseline. Test them on separate tracks where appropriate. A wrong view, stale resource, skipped draw or frozen animation needs a causal fix first.
